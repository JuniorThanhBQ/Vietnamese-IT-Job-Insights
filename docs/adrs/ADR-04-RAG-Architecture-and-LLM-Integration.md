# ADR-04: RAG Architecture and LLM Integration with LangChain and Gemini

## Status
Approved

## Context
The project goals require building a virtual assistant to support users in searching for jobs using natural language through Retrieval-Augmented Generation (RAG). Users should be able to ask complex, conversational questions about IT jobs in Vietnam (e.g., "Recommend junior Python jobs in Ho Chi Minh City that support remote work").

However, the implementation is subject to strict constraints:
1. **Low-spec hosting system (8GB RAM, i7 Gen 4 CPU):** Hosting a local LLM (e.g., Llama or Mistral) is impossible. We must use cloud-based APIs.
2. **API Quotas and Rate Limits:** Since we are using free tier Gemini API keys, we face strict Rate Limits (Requests Per Minute - RPM).
3. **Interactive Premium UX:** A typical LLM response can take several seconds to complete, which degrades user experience. The system must support streaming responses.
4. **Clean Code and Maintainability:** RAG workflows require structured prompts, context retrieval, and model orchestration, which must align with backend modular architecture.

## Decision
We will implement the following RAG architecture and LLM integration:

1. **Retrieval Orchestration:** Use **LangChain** (specifically `langchain-core` and specialized lightweight wrappers) to structure prompts and manage chat history.
2. **LLM Engine:** Use **Gemini 1.5 Flash** (`gemini-1.5-flash`) via the Developer API. This model is extremely fast, has a huge context window, and is free-tier friendly.
3. **Key Rotation Integration:** Integrate our key rotation mechanism (developed in Phase 2) into the LLM request layer to dynamically switch API keys upon hitting 429 (Rate Limit) or 403 (Quota Exceeded) errors.
4. **RAG Workflow:**
   * User submits a query to FastAPI.
   * FastAPI converts the query to a 768-dimensional embedding using `GeminiEmbeddingService`.
   * FastAPI queries the database via `pgvector` using Cosine Distance to retrieve the top-K (e.g., K=5) most relevant active job postings.
   * FastAPI formats the retrieved job data (Title, Company, Salary, Location, Requirements, Description) into a text context.
   * LangChain merges the system prompt, chat history context, and retrieved job context, and sends it to the Gemini LLM.
5. **Streaming Endpoint:** Expose a Server-Sent Events (`text/event-stream`) route `/api/v1/assistant/chat` in FastAPI. The response will be yielded chunk-by-chunk to the React frontend as it is generated by Gemini.

## Rationale
1. **Resource Efficiency:** Leveraging Gemini 1.5 Flash offloads all heavy LLM computations to Google's cloud infrastructure, maintaining local RAM usage below the 8GB limit.
2. **Resilience:** Round-robin key rotation across multiple free tier API keys ensures high availability for the assistant chat.
3. **Enhanced UX:** Streaming responses chunk-by-chunk (SSE) ensures a responsive interface and eliminates wait latency.
4. **Standardization:** LangChain simplifies context formatting, history tracking, and prompt management, reducing custom boilerplate.

## Consequences
### Positive
* Zero RAM overhead for LLM hosting on the developer's local machine.
* Smooth, real-time typing effect in the user interface via SSE streaming.
* Low risk of quota blockages due to automated key rotation.
* Clean separation of concerns (FastAPI handles retrieval and streaming, LangChain structures LLM prompts).

### Negative
* LangChain libraries introduce dependency size and minor FastAPI startup overhead.
* Network dependency on Gemini API introduces external latency.
